# Research: Pi extension testing practices for 0.84.x

## Summary

Pi 0.84.2 gives one explicit extension-testing instruction: load an extension with `pi -e ./my-extension.ts` for a quick test. It does **not** prescribe a unit-test runner, mock library, extension test harness, or end-to-end workflow. Vitest, inline extension factories, `ExtensionRunner`, faux model streams, direct component rendering, Node's test runner, and a headless terminal are first-party repository practices—not documented requirements for third-party extensions.

For the planned Pi UI Surface packages, use layered behavior tests: test pure logic and registered callbacks directly; test extension wiring through a recording `ExtensionAPI` or Pi's public runner/runtime seams; render components at a width and assert visible widths/ANSI behavior; reserve actual terminal runs for emulator, input, resize, motion, and visual-quality claims.

**Scope/version.** Repository dependency: `package.json` requests `@earendil-works/pi-coding-agent ^0.84.2`; installed metadata reports `0.84.2`. Upstream citations below are pinned to tag [`v0.84.2`](https://github.com/earendil-works/pi/releases/tag/v0.84.2). Local first-party files examined: `node_modules/@earendil-works/pi-coding-agent/docs/extensions.md`, `docs/tui.md`, `examples/extensions/*`, `dist/index.d.ts`, `dist/core/extensions/types.d.ts`, `loader.d.ts`, `runner.d.ts`, and the installed package metadata.

## Findings

1. **No prescribed automated plugin runner/workflow (severity: advisory).** The extension guide says only “Test with `--extension` (or `-e`)” and calls `pi -e` a quick-test path; auto-discovered locations are preferred when testing `/reload`. It names no Vitest/Jest/Node test runner, fixtures, mocks, or CI workflow. This is the sole explicit extension-testing recommendation found. [Extension docs](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/extensions.md) (local: `node_modules/@earendil-works/pi-coding-agent/docs/extensions.md`).

2. **Runner choices are first-party practice, not extension API policy.** `packages/coding-agent` uses `"test": "vitest --run"` and declares Vitest 4.1.9; `packages/tui` instead uses Node's built-in test runner over `test/*.test.ts`. Therefore consumers should choose the runner that fits their package; matching Vitest is convenient for coding-agent-style tests, but not officially required. [coding-agent package metadata](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/package.json) (local installed `node_modules/@earendil-works/pi-coding-agent/package.json`); [TUI package metadata](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/package.json).

3. **First-party coding-agent tests load inline factories and drive a real runtime.** `createTestExtensionsResult()` creates a shared runtime/event bus, loads inline `ExtensionFactory` values, and returns the loaded extensions plus runtime; `createTestResourceLoader()` injects that result. The session harness accepts `extensionFactories`, uses faux model stream responses, and captures events. This supports behavior tests without loading user files or making paid provider calls. These helpers live under upstream `test/` and are **not** package exports; copy the pattern, do not import them as a supported dependency. [utilities](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/utilities.ts); [test harness](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/test-harness.ts); [suite harness](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/suite/harness.ts). Upstream contributor instructions additionally require the suite faux provider rather than real APIs/keys/tokens; that is first-party repository guidance, not extension-user documentation. [AGENTS.md](https://github.com/earendil-works/pi/blob/v0.84.2/AGENTS.md).

4. **`ExtensionRunner` drives events and `ExtensionContext` deterministically.** First-party runner tests instantiate `ExtensionRunner`, bind actions, select a UI mode with `setUIContext()`, call `createContext()`, and assert `mode`/`hasUI`; no UI defaults to print mode, while RPC and TUI modes expose UI. The public declaration also exposes typed `emit`, `emitInput`, `emitToolCall`, `emitToolResult`, `emitContext`, provider hooks, renderer lookup, tool lookup, and context creation. [runner tests](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/extensions-runner.test.ts); [runner source](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/src/core/extensions/runner.ts). Installed public export evidence: `node_modules/@earendil-works/pi-coding-agent/dist/index.d.ts` exports `createExtensionRuntime`, `ExtensionRunner`, `discoverAndLoadExtensions`, `wrapRegisteredTool(s)`, and all extension event/context types.

5. **Events are tested at two useful levels.** At the narrow level, invoke captured handlers or runner `emit*` methods with typed event objects and a controlled context, then assert chained transforms, mutations, blocks, result patches, and errors. At the integrated level, inject extension factories into `AgentSession` with faux responses and assert emitted lifecycle/tool/message events and session entries. Existing suites cover input source/streaming behavior and handler errors, compaction cancellation/custom results/order/fallback, and real example behavior. [input-event tests](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/extensions-input-event.test.ts); [compaction tests](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/compaction-extensions.test.ts); [tested custom-compaction example](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/compaction-extensions-example.test.ts).

6. **Extension discovery is a separate behavior seam.** First-party tests create temporary `.ts` extension files and verify configured/standard discovery, tool and renderer registration, and syntax/load errors. Use this only for package entrypoint/discovery tests; most behavior tests should import a factory directly to avoid jiti/filesystem noise. [discovery tests](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/extensions-discovery.test.ts); [extension examples usage](https://github.com/earendil-works/pi/tree/v0.84.2/packages/coding-agent/examples/extensions).

7. **A recording `ExtensionAPI` is the lightest stable wiring seam (inferred practice).** Invoke the default factory with a small test double that records `on`, `registerTool`, `registerCommand`, `registerMessageRenderer`, `registerMarkdownTransformer`, etc.; then call the captured definitions. This directly verifies registration and behavior while requiring only public `ExtensionAPI`/callback types. It is an inference from the factory contract and upstream example test that captures `session_before_compact`, not an explicit documented workflow. [extension factory/API types](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/src/core/extensions/types.ts); [example test](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/compaction-extensions-example.test.ts).

8. **Tool definitions and wrappers have strong public behavior seams.** A captured `ToolDefinition` can be tested through `prepareArguments`, `execute`, `renderCall`, and `renderResult`; pass controlled `AbortSignal`, update callback, `ExtensionContext`, result options, theme, and `ToolRenderContext`. Built-in wrappers can delegate to public `createReadTool`, `createBashTool`, `createEditTool`, and `createWriteTool`, exactly as the first-party renderer example does. Assert parameter/result/detail shape, abort/update propagation, partial/expanded/error views, width, and wrapper delegation separately. [tool types](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/src/core/extensions/types.ts); [built-in renderer wrapper](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/examples/extensions/built-in-tool-renderer.ts); [todo execute/render example](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/examples/extensions/todo.ts). Official docs warn that overridden built-ins must preserve exact result/detail shapes and that omitted renderer slots inherit built-in rendering. [extension docs](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/extensions.md).

9. **TUI components/renderers are intentionally callable without a live terminal.** `Component.render(width): string[]`, optional `handleInput(data)`, and `invalidate()` are the core contract. First-party examples instantiate `Text`, `Box`, or custom classes in message/tool renderers; `custom-message.test.ts` directly constructs `CustomMessageComponent`, renders it, changes `outputPad`, and asserts the renderer receives updated options. Recommended behavior tests can call renderer functions, then call the returned component's `render(width)`; drive input with encoded key data and assert state/callbacks; call `invalidate()` and render again after theme/state changes. [TUI docs](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/tui.md) (local same path under installed package); [custom-message test](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/test/custom-message.test.ts); [message renderer example](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/examples/extensions/message-renderer.ts).

10. **Autocomplete providers expose pure delegation/filter seams.** The official example factors token parsing, repo parsing, formatting/filtering, and provider creation; the provider calls its predecessor for non-matches, aborted loads, missing data, or empty results, and delegates completion application/file-trigger behavior. Tests should supply a predecessor spy, line/cursor tuples, an `AbortSignal`, and fixed issue data; assert own suggestions and fallback calls. The example's helpers are not exported, so planned packages should export pure provider factories if reuse/testing matters. [autocomplete example](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/examples/extensions/github-issue-autocomplete.ts); [documented provider pattern](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/extensions.md).

11. **Markdown transformers are direct pure-function seams; upstream has little dedicated test coverage.** Public type: `(markdown, { messageType, isStreaming, availableWidth }) => string`. Official docs specify display-only transformation, load-order chaining, and synchronous/inexpensive work; stored session/model context is unchanged. Test the transformer directly across all message types, streaming states, and widths, then separately test factory registration. No dedicated v0.84.2 first-party transformer test was found, so claims about integration with the built-in Markdown renderer need a component/TUI test. [types](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/src/core/extensions/types.ts); [extension docs](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/extensions.md).

12. **Width/ANSI/CJK utilities and patterns are mature.** Official TUI docs require every rendered line to fit `width`, and name public `visibleWidth`, `truncateToWidth`, and `wrapTextWithAnsi`; Pi appends SGR and OSC-8 resets per rendered line. Upstream tests cover ANSI-insensitive width, reset/style preservation, OSC-8 links, tabs, combining/Indic clusters, CJK/Japanese double-width text, Thai/Lao/Myanmar, flags/emoji/ZWJ/modifiers, and clipping overlays at CJK boundaries. Mirror these as table-driven boundary cases and assert `visibleWidth(line) <= width`, not JS `length`. [TUI docs](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/tui.md); [truncate/width tests](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/test/truncate-to-width.test.ts); [ANSI wrapping tests](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/test/wrap-ansi.test.ts); [regional-indicator regression](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/test/regression-regional-indicator-width.test.ts); [CJK overlay regression](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/test/regression-overlay-cjk-boundary.test.ts).

13. **Headless whole-screen rendering exists, but as test-only upstream machinery.** TUI tests pair `TuiMainScreen` with `test/virtual-terminal.ts` (backed by `@xterm/headless`), render at fixed rows/columns, wait for rendering, inspect screen lines/writes, resize, and exercise overlays. `VirtualTerminal` and test themes live under upstream `test/`; they are not demonstrated as stable package exports. Planned UI Surface packages may copy the architecture or use `@xterm/headless` directly, but should not deep-import upstream test files. [render tests](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/test/tui-render.test.ts); [virtual terminal](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/test/virtual-terminal.ts); [overlay tests](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/test/overlay-options.test.ts); [test themes](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/test/test-themes.ts).

14. **Theme tests should emphasize invalidation and semantic tokens.** Official docs say use the callback-provided theme, rebuild pre-baked colored content during `invalidate()`, and use theme callbacks when possible. Behavior tests should render with two deterministic themes, call `invalidate()`, rerender, and assert the new ANSI sequences/tokens and unchanged visible text/width. This is an explicit component-design recommendation; the deterministic fake-theme testing method is inferred. [TUI theming/invalidation docs](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/tui.md); [theme docs](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/themes.md).

15. **Motion is mostly tested as deterministic frames, not elapsed-time fidelity.** First-party render tests manually mutate a spinner-like component through `| / - \\`, request renders, and inspect terminal output. Examples use real `setInterval` for working indicators/editors and require cleanup; no v0.84.2 fake-timer Loader/theme suite was found. For planned packages, extract `frameAt(index/time)` and test frames as pure data; use fake timers only around package-owned scheduling; assert start/stop/dispose clears timers and calls `requestRender`. Treat cadence/smoothness as manual. [render tests](https://github.com/earendil-works/pi/blob/v0.84.2/packages/tui/test/tui-render.test.ts); [working indicator example](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/examples/extensions/working-indicator.ts); [rainbow editor example](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/examples/extensions/rainbow-editor.ts).

16. **Real TUI/manual testing remains necessary (severity: residual risk).** Unit/headless tests cannot prove: exact colors/contrast in a user's emulator; font-dependent ambiguous-width glyphs; IME candidate-window placement; Kitty keyboard/key-release behavior; mouse/focus interactions; terminal resize races; scrollback preservation/flicker/tearing; animation smoothness and CPU use; OSC title/notification support; hyperlinks/images across Kitty/iTerm2/Ghostty/WezTerm/Warp; shell/PTY behavior; or human readability at realistic transcript density. Run `pi -e` in representative terminals and widths, switch themes, resize during streaming, exercise keyboard/IME/mouse, and inspect raw ANSI with `PI_TUI_WRITE_LOG` where needed. [TUI docs, including IME, overlays, and debug log](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/tui.md); [interactive overlay QA extension](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/examples/extensions/overlay-qa-tests.ts).

## Recommended test layers for Pi UI Surface

1. **Pure tests:** formatting, width allocation, transformer, autocomplete matching/delegation, frame selection, tool result mapping.
2. **Registration tests:** recording `ExtensionAPI`; assert event/tool/renderer/transformer/provider registration and invoke captured callbacks with minimal typed contexts.
3. **Public Pi runtime tests:** `createExtensionRuntime` + `ExtensionRunner`, or public AgentSession SDK with a faux provider, when middleware order/context/session behavior matters.
4. **Component contract tests:** render at widths including 0/1/narrow/wide; assert line count/content, `visibleWidth <= width`, ANSI balance, CJK/emoji boundaries, input, invalidation, theme changes, partial/expanded states.
5. **Headless terminal tests:** package-owned xterm-headless harness for compositing, cursor, overlays, diff rendering, resize, and final screen state.
6. **Manual matrix:** actual Pi via `pi -e`, multiple emulators, themes, widths, IME, motion, mouse, links/images, and streaming/resizing.

Avoid deep imports from Pi `dist/core/...` or upstream `test/...`: installed package `exports` exposes only `.` plus RPC/client entrypoints. Root-exported declarations are the compatibility boundary; test-only helpers are examples to reproduce locally.

## Gaps

- No first-party v0.84.2 automated test dedicated to `addAutocompleteProvider` or `registerMarkdownTransformer` was found; proposed tests are derived from public contracts/examples.
- Upstream test helpers are not shipped in `@earendil-works/pi-coding-agent`; a reusable third-party harness must be maintained by this repository or built only from root exports.
- Headless behavior still depends on xterm's model and cannot establish parity with every terminal emulator/font/OS.
- No automated evidence can establish visual appeal, perceived motion quality, or all accessibility/IME behavior; retain a documented manual matrix.
