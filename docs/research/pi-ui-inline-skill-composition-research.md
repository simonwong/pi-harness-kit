# Research: Pi UI #14 — Inline multi-Skill composition in the editor

- Issue: [pi-harness-kit#14 — 塑造并实现编辑器内多 Skill 组合](https://github.com/simonwong/pi-harness-kit/issues/14) (roadmap row 4, Input Surface, `docs/product-roadmap.md`)
- Accessed: 2026-08-27
- Local evidence base: installed `@earendil-works/pi-coding-agent@0.84.2` and `@earendil-works/pi-tui@0.84.2` under `node_modules/` (declared in root `package.json`).
- Limitation of this run: no shell tool was available (so `gh` could not be run), and the sandbox proxy blocked direct fetches of github.com / raw.githubusercontent.com / unpkg / fossies. Issue #14's body could not be fetched verbatim; requirements below are taken from the roadmap row, the quality contract, and the task brief. All other sources were read via search-provider-retrieved full content or local installed files.

## Summary

Inline multi-Skill composition is **mostly feasible on documented public APIs** of pi 0.84.2: a stacked autocomplete provider (`ctx.ui.addAutocompleteProvider`) with multi-line-aware `getSuggestions`/`applyCompletion`, a skill catalog from `pi.getCommands()` (`source === "skill"`), and submission handling via the `input` event (transform) plus optionally `before_agent_start` injection and `registerMessageRenderer` reusing the exported `SkillInvocationMessageComponent`. The **one hard gap** is auto-popup on `/` typed mid-text or on later lines: the pi-tui editor gates `/` auto-trigger to start-of-message on line 0, and `/` is explicitly excluded from provider `triggerCharacters` (confirmed in installed source and upstream issue #4703 / commit b7e721c). Working public-API fallbacks: Tab-forced completion anywhere, or `ctx.ui.setEditorComponent` (public, but claims the editor resource, which the v1 architecture explicitly does not claim). Two existing pi extensions (cnife, herbertgao) already ship close variants of this exact capability and are the primary design references; datspike's extension is the reference for the editor-seam approach and the absolute-path false-positive fix.

## Findings

### 1. Architecture fit (against `docs/architecture/pi-ui-public-api.md` and ADR 0001)

1. **The planned seam already matches the architecture doc.** `docs/architecture/pi-ui-public-api.md` ("Input" section) prescribes exactly one composite autocomplete provider via `ctx.ui.addAutocompleteProvider()` during `session_start`, deterministic Pi UI trigger priority, delegation to the previous provider exactly once, and "Multi-Skill insertion and submission transformations remain visible, understandable, and undoable. v1 does not replace the main editor component." The quality contract (`docs/engineering/pi-ui-v1-quality-contract.md`, conditional gate "Autocomplete/input") requires evidence for: deterministic priority, previous-provider delegation exactly once, insertion/removal/undo/dismissal, failure delegation, plus a real-IME Ghostty smoke covering composition, discovery, combination, removal, undo, dismissal, submission, and native delegation. Config section `input.multiSkill.enabled` is already reserved in the versioned `pi-ui.json` contract.
2. **Native pi skill expansion is whole-message and single-skill.** In installed source `node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js` (`_expandSkillCommand`, ~line 930): expansion only runs when `text.startsWith("/skill:")`, expands exactly one skill into `<skill name="..." location="...">\nReferences are relative to <baseDir>.\n\n<body>\n</skill>` optionally followed by `\n\n<args>`, and returns the original text for unknown skills. `expandPromptTemplate` (`dist/core/prompt-templates.js`) is likewise whole-text. So `/skill:a … /skill:b` or mid-text `/skill:a` is **never** expanded natively — this is the gap the Capability owns. (Implementation detail, not a guaranteed contract, but consistent with the documented lifecycle in `docs/extensions.md`: "skill commands (`/skill:name`) expanded to skill content" happens after the `input` event.)
3. **The expansion block format is semi-public.** `parseSkillBlock` and `ParsedSkillBlock` are exported from the package root (`dist/index.d.ts`, `dist/core/agent-session.js` lines 38-50). Its regex is anchored `^<skill name="..." location="...">\n...\n</skill>(\n\nuserMessage)?$` — exactly one block. The TUI's `SkillInvocationMessageComponent` (exported from root; `dist/modes/interactive/components/skill-invocation-message.d.ts`) renders one block as the native collapsible `[skill]` card. Multi-block messages do not match `parseSkillBlock`, so a natively-submitted multi-skill message would render as raw text unless the Capability registers its own renderer.
4. **Resource ownership table anticipates this Capability but forbids the strongest trigger path.** The doc's ownership table says "custom editor: Not claimed in v1; existing editor wins" and "autocomplete: Wrap current provider and delegate exactly once". The datspike extension (below) achieves mid-text auto-popup only by claiming the editor via `setEditorComponent` — a documented public API, but one that violates the current v1 boundary and would conflict with any other editor-replacing extension. This is the central scope decision for `/to-spec`.

### 2. Public-API feasibility (pi 0.84.2, documented vs installed-source-only)

5. **Sufficient, documented:**
   - `ctx.ui.addAutocompleteProvider((current) => provider)` — stacked provider; `getSuggestions(lines, cursorLine, cursorCol, { signal, force })` receives **all editor lines and the exact caret**, so mid-text and later-line detection is fully implementable in provider code (`docs/extensions.md` "Autocomplete Providers"; `AutocompleteProvider` type in `node_modules/@earendil-works/pi-tui/dist/autocomplete.d.ts`). Canonical example: `node_modules/@earendil-works/pi-coding-agent/examples/extensions/github-issue-autocomplete.ts`.
   - `applyCompletion(lines, cursorLine, cursorCol, item, prefix)` may return an arbitrary new `{ lines, cursorLine, cursorCol }` — insertion, replacement, and removal of `/skill:` tokens anywhere (including multi-line) are fully under Capability control. The pi-tui editor pushes an undo snapshot before applying a completion (installed `pi-tui/dist/components/editor.js`, `tui.select.confirm` / Tab branches, ~lines 520-575), so completions are natively undoable as one unit.
   - `pi.getCommands()` returns `{ name, description?, source: "extension" | "prompt" | "skill", sourceInfo }` with `sourceInfo` as canonical provenance — sufficient skill catalog data (name + description + path/baseDir) without re-walking the filesystem (`docs/extensions.md`; `dist/core/slash-commands.d.ts`).
   - `input` event: `transform` (rewrite text before native skill/template expansion) or `handled`, with `event.source` ("interactive" | "rpc" | "extension") and `event.streamingBehavior` for steer/followUp routing (`docs/extensions.md` "Input Events"; expansion order verified in `agent-session.js` `prompt()`, ~lines 780-800).
   - `before_agent_start` can inject a persistent displayed custom message (`message: { customType, content, display: true }`), and `pi.registerMessageRenderer` + root-exported `SkillInvocationMessageComponent`, `UserMessageComponent`, `convertToLlm` allow native-looking collapsible skill blocks for multi-skill submissions.
   - `ctx.ui.setEditorText/getEditorText/pasteToEditor`, `ctx.ui.onTerminalInput(handler)` (raw input listener returning `{ consume, data }`), `pi.registerShortcut` — all documented (`docs/extensions.md`; `dist/core/extensions/types.d.ts` `ExtensionUIContext`).
6. **NOT sufficient (the trigger gap):** auto-opening the suggestion popup when `/` is typed mid-text or on line > 0 is impossible through the provider API alone. Installed `pi-tui/dist/components/editor.js`:
   - `insertCharacter` auto-triggers on `/` only when `isAtStartOfMessage()` (requires `cursorLine === 0` and empty-or-`/` text before cursor); `isSlashMenuAllowed()` is literally `cursorLine === 0` (~lines 1770-1800).
   - `setAutocompleteTriggerCharacters` explicitly **drops `/`** and whitespace from provider-declared triggers (~line 2160: `character === "/"` is skipped). This matches upstream [earendil-works/pi#4703](https://github.com/earendil-works/pi/issues/4703) and [commit b7e721c](https://github.com/earendil-works/pi/commit/b7e721cb38973eb6b58f8eb6988177aab662ea75), which added `AutocompleteProvider.triggerCharacters` (present in our 0.84.2) but deliberately kept `/` editor-owned.
   - `tryTriggerAutocomplete`/`requestAutocomplete` are private; the only programmatic open paths are typing a trigger char at a token boundary or Tab.
7. **Documented fallback that works today:** pressing **Tab** with the caret after a mid-text `/xx` token reaches the provider. `handleTabCompletion` → (non line-0-slash context) → `forceFileAutocomplete(true)` → `requestAutocomplete({ force: true })` → `provider.getSuggestions(..., { force: true })` (editor.js ~lines 1820-1840). A skill provider can honor `force` and return matches for a `/query` token at the caret on any line. This gives "type `/xx`, Tab, pick" everywhere with zero private API — but no auto-popup on `/`.
8. **Unsafe dependencies to reject:** monkey-patching `CustomEditor.prototype.handleInput` and calling the private `tryTriggerAutocomplete()` via runtime cast — this is exactly what `@herbertgao/pi-inline-skills` does (source retrieved via jsdelivr: `cdn.jsdelivr.net/npm/@herbertgao/pi-extensions@2026.8.7/node_modules/@herbertgao/pi-inline-skills/src/index.ts`), and what the #4703 reporter explicitly called "fragile". Also unsafe: depending on `parseSkillBlock`'s exact regex or `_expandSkillCommand`'s block string beyond what the exported `parseSkillBlock`/`SkillInvocationMessageComponent` signatures imply.
9. **Mode safety:** the `input` event fires in RPC/JSON/print modes too. The Capability must no-op outside `ctx.mode === "tui"` (per PRODUCT.md and the architecture doc), which means multi-skill text submitted via RPC remains native (unexpanded beyond the first line-start skill) — acceptable native parity, must be stated in the spec.

### 3. Source-reuse fit (candidate implementations)

10. **`@cnife/pi-inline-skill-completion`** ([npm](https://www.npmjs.com/package/@cnife/pi-inline-skill-completion), [README](https://github.com/CNife/pi-extensions/blob/main/packages/inline-skill-completion/README.md)) — **closest to issue #14's full scope.** Documented behavior: non-line-start `/` auto-pops fuzzy skill candidates; line-start `/` delegates to native; on submit it parses **all** `/skill:xxx` tokens, prepends skill blocks in order, deletes the first line-start token with its trailing separator, keeps later tokens literally in the sentence; unknown skill/read failure leaves the token unexpanded; total failure falls back to a native user message; streaming submit respects `streamingBehavior` via `deliverAs` steer/followUp. Mechanism: `input` event returns `action: "handled"`, then `pi.sendMessage({ customType: "inline-skills", content: <fully expanded>, details: { blocks, body } })`, and a `registerMessageRenderer` that renders each block with the native `SkillInvocationMessageComponent` and the body with `UserMessageComponent`. Claims line-start single-skill expansion is byte-identical to native. How it auto-triggers mid-text is not shown in the README (likely a custom editor or the patch trick); that detail needs source verification before reuse.
11. **`@herbertgao/pi-inline-skills`** (source retrieved from jsdelivr, see Finding 8) — **the most transparent submission design and a fully readable implementation.** Key differences: (a) `input` returns `action: "transform"` with the text **unchanged**, stashing expanded content; (b) `before_agent_start` injects one custom message wrapping all newly-referenced skills in an `<inline_skills>…</inline_skills>` envelope ("already loaded, do not load again"); (c) it tracks `loadedSkills` per session (via `appendEntry` + a `tool_result` hook that notices when the agent `read`s a SKILL.md) to avoid re-injecting already-loaded skills; (d) its autocomplete provider merges skill items with the delegated provider's items (`mergeAutocompleteItems`), prefers native commands at line-start, and its `applyCompletion` replaces just the `/query` token with `/name` + trailing space for chaining. Its trigger, however, relies on the prototype patch (Finding 8). The transform-and-inject approach keeps the user's literal text as the submitted user message — the most "transparent submission" of all candidates.
12. **`@datspike/pi-inline-slash-extension@0.1.0`** ([GitHub](https://github.com/datspike/pi-inline-slash-extension), [npm](https://www.npmjs.com/package/@datspike/pi-inline-slash-extension)) — MIT, created 2026-04-05, 9 weekly downloads, 0 dependents (low maturity). Scope: inline `/` autocomplete mid-text and on line 2+, plus a submit bypass so leading absolute paths (`/tmp/log.txt`) are sent as normal messages instead of unknown commands. Architecture (from README/ARCHITECTURE docs): entry `extensions/inline-slash.ts` activates on `session_start` when `ctx.hasUI`; catalog built **only** from `pi.getCommands()`; wraps `CustomEditor` in `src/inline-slash/editor.ts` and registers it via `ctx.ui.setEditorComponent(...)`; submit routing via `createInlineSlashSubmitStrategy` using `sendUserMessage` only for the path-bypass; `/unknown` stays delegated; `@` file completion stays delegated. Its `docs/UPSTREAM-SEAMS.md` explicitly requests from pi upstream "a public editor seam for autocomplete open/refresh/close and a pre-dispatch submit hook" — independent confirmation of Finding 6. It does **not** implement multi-skill expansion. Value to us: catalog-from-`getCommands()` pattern, absolute-path false-positive fix, and the upstream-seam wishlist.
13. **gemini-cli `useSlashCompletion.ts`** ([file at f8541cf7](https://github.com/google-gemini/gemini-cli/blob/f8541cf7/packages/cli/src/ui/hooks/useSlashCompletion.ts)) — full source reviewed. Transferable data model: a pure parser producing `{ hasTrailingSpace, commandPathParts, partial, currentLevel, leafCommand, isArgumentCompletion }`, separate `useCompletionPositions` computing `{start,end}` replacement ranges, prefix-filter fast path with fzf fuzzy fallback (WeakMap-cached per command level), and explicit `isPerfectMatch` semantics. Note gemini-cli **also** gates slash completion to `cursorRow === 0 && isSlashCommand(line)` in [`useCommandCompletion.tsx`](https://github.com/google-gemini/gemini-cli/blob/d2cd12a7/packages/cli/src/ui/hooks/useCommandCompletion.tsx) — mid-text slash is unsolved there too; `@`-completion scans backwards from the caret with backslash-escape handling (a good model for token extraction). Cautionary follow-ups: [PR #20136](https://github.com/google-gemini/gemini-cli/pull/20136) (don't auto-descend into subcommands or auto-append a space for executable commands) and [PR #15287](https://github.com/google-gemini/gemini-cli/pull/15287) (keep sibling suggestions on exact match; exact match sorts first). Not embeddable (React/Ink); the parser/range design and its regression lessons transfer directly to a pure Pi UI module.
14. **openai/codex [PR #317](https://github.com/openai/codex/pull/317)** (merged 2025-04-19, +184/-1, 3 files) — the original `/command` autocomplete. UI decisions worth copying: live filter popup as soon as leading `/` is typed; Up/Down navigation; **Enter on a partial command fills the command without submitting** (first Enter swallowed, second Enter submits); only registered commands ever autocomplete; unknown slash input still errors natively. Later codex work reinforces draft preservation: [PR #23950](https://github.com/openai/codex/pull/23950) keeps text after a completed command as inline arguments instead of discarding it — directly relevant to "replacement must not eat surrounding prose". Contrast with pi-tui's editor: in installed `editor.js` (~line 555), confirming a completion whose `prefix.startsWith("/")` **falls through to submit** — so a Pi UI skill provider must return a prefix that does not start with `/` (e.g. the bare query) and do its own token replacement in `applyCompletion`, or Enter will submit the whole message mid-composition. This is a critical, non-obvious integration detail.
15. **Web-editor slash menus (interaction reference only, non-embeddable):** Tiptap's [Suggestion utility](https://github.com/ueberdosis/tiptap-docs/blob/main/src/content/editor/api/utilities/suggestion.mdx) (plugin key, `allow`/`char`, query range tracking), [prosemirror-slash-menu](https://github.com/emergence-engineering/prosemirror-slash-menu) (opens on `/` "in an empty paragraph or after a space by default", custom opening conditions), and Lexical's [`useBasicTypeaheadTriggerMatch`](https://github.com/facebook/lexical/blob/main/packages/lexical-react/src/LexicalTypeaheadMenuPlugin.tsx) (trigger must be "preceded by whitespace or the start of the line", `minLength`/`maxLength`, punctuation boundary set). The convergent interaction rule across all three — trigger only at token boundaries, bounded query charset, dismiss on boundary violation — is exactly the false-positive-avoidance rule a Pi UI provider should implement for `/` (and it matches pi-tui's own `@`/`#` token-boundary logic). None of these can run in pi's TUI.

### 4. Interaction semantics and edge cases (evidence-backed)

16. **False positives (paths/URLs/code):** require `/` at a token boundary (line start or after whitespace) **and** a query matching the skill-name charset `[a-z0-9-]`, then only show the popup when at least one catalog entry matches. `/tmp/x`, `https://a/b`, `a/b`, `./x` never satisfy both. Prior art: datspike's leading-absolute-path submit bypass; [qwen-code PR #3743](https://github.com/QwenLM/qwen-code/pull/3743) (path-like `/api/...` inputs must not be treated as commands); [docmost PR #1897](https://github.com/docmost/docmost/pull/1897) (disable slash menu inside code blocks — in a terminal editor, the analog is: don't trigger when the token contains `/` beyond the leading one or when no skill matches); Claude Code's pasted-path hijack [bug report](https://www.stepcodex.com/en/issue/bug-slash-command-autocomplete-hijacks-pasted) shows why paste must never trigger (pi-tui already suppresses autocomplete during paste — `handlePaste` calls `cancelAutocomplete()` and inserts atomically).
17. **IME/undo/multi-line:** pi-tui's editor inserts any printable data chunk atomically (IME commits arrive as multi-char chunks → one undo unit), pushes undo snapshots before completions, emits the hardware `CURSOR_MARKER` for IME candidate-window placement **even while the autocomplete list is visible** (editor.js render, ~line 430), debounces provider calls 20 ms for attachment-like tokens, and aborts stale provider requests via `options.signal`. Providers must therefore be synchronous-fast (catalog preloaded at `session_start` from `pi.getCommands()`, no I/O in `getSuggestions`) and honor the abort signal. General TUI IME risk context: [opentui issue #942](https://github.com/anomalyco/opentui/issues/942), [Kiro issue #6664](https://github.com/kirodotdev/Kiro/issues/6664) — Enter during composition can mis-submit; the quality contract's real-IME Ghostty smoke is the right gate (automated tests cannot prove IME behavior).
18. **Submission semantics choice (the main spec decision):**
    - **(a) `input` transform to fully expanded text** — simplest; but the stored/transcript user message becomes the verbose expanded form, and multi-block text won't parse as a native skill block (renders raw).
    - **(b) `handled` + custom message (cnife)** — full rendering control (native collapsible blocks per skill); but the message becomes `customType`, changing session/tree/fork semantics vs a real user message.
    - **(c) `transform` (unchanged text) + `before_agent_start` injection (herbertgao)** — the user message stays exactly as typed (maximally transparent and reversible); skill content arrives as a separate persistent custom message with native block rendering; needs the loaded-skills tracking to avoid double injection. Recommended direction for "transparent submission"; verify `before_agent_start` messages survive compaction/branching acceptably.
19. **Removal/replacement:** in v1 the inserted skill token is plain text (`/skill:name ` with trailing space, per cnife), so removal is ordinary deletion (backspace/delete-word/kill-ring all work natively) and replacement is delete + re-complete. No chip/widget decorations exist in the editor API — do not promise them. Esc dismisses the popup natively (`tui.select.cancel`).

### 5. Prototype shortlist and recommendations

20. **Recommended build/reuse plan:**
    - **Build** the Capability as a pure trigger/classifier module + one composite autocomplete provider + one `input`/`before_agent_start` submission module inside `packages/pi-ui-input`, per the existing architecture doc. No runtime dependency on any third-party extension.
    - **Reuse as design references (read their source before `/to-spec`):** herbertgao/pi-inline-skills (submission design, provider merging, `applyCompletion` token surgery) and cnife/pi-inline-skill-completion (expansion rules table, edge-case matrix, renderer composition). Both are MIT-licensed npm packages.
    - **Reference for scope decision:** datspike (editor-seam cost/benefit, absolute-path bypass, upstream-seam request).
    - **Reference only:** gemini-cli (parser data model, perfect-match and auto-space pitfalls), codex #317 + #23950 (Enter-to-fill-not-submit, draft preservation), Tiptap/prosemirror-slash-menu/Lexical (token-boundary trigger rule).
21. **Trigger-strategy options for `/to-spec` (pick one):**
    - **Option A (public-only, v1-safe):** auto-popup only where pi natively triggers (line-0 start); everywhere else, explicit **Tab** after `/xx` opens the skill popup via `force`. Lowest risk, fully within the architecture boundary, but `/`-typed auto-popup mid-text is absent.
    - **Option B (public API, boundary change):** `ctx.ui.setEditorComponent` wrapping `CustomEditor` to trigger on mid-text `/` (datspike's approach). Documented API, but claims the editor resource — requires amending the architecture doc's "custom editor: Not claimed in v1" rule and accepting conflicts with other editor-replacing extensions.
    - **Option C (reject):** prototype-patch `CustomEditor.prototype.handleInput` + private `tryTriggerAutocomplete` (herbertgao). Fragile private dependency; violates the public-API-only constraint in PRODUCT.md.
    - **Option D (parallel track):** file/​upvote an upstream pi request for a public autocomplete open/refresh seam or `/` as an opt-in provider trigger (datspike's UPSTREAM-SEAMS.md asks for exactly this; #4703 shows upstream accepts such requests).

## Gaps / unresolved questions for `/to-spec`

1. **Issue #14 body was not fetched** (no `gh`, GitHub blocked by sandbox proxy). Requirements were reconstructed from `docs/product-roadmap.md` row 4, the quality contract, and the task brief. Re-read the issue before spec freeze.
2. **Trigger strategy decision (Finding 21, Option A vs B)** is the highest-impact open question: accept Tab-forced completion mid-text for v1, or claim the editor via `setEditorComponent` (architecture amendment + conflict rules needed).
3. **Submission semantics (Finding 18, a/b/c)**: which shape is "transparent" enough — expanded user message, custom message replacement, or literal message + injected skill context? Needs a product call; option (c) best matches "visible, understandable, reversible" but is the least native in session-model terms.
4. **cnife's mid-text trigger mechanism** is not visible in its README; clone/read `packages/inline-skill-completion` source during `/to-spec` to confirm whether it also patches the editor prototype.
5. **Whether `/skill:`-token expansion should also cover prompt templates and extension commands inline** (datspike completes all commands mid-text) or remain skills-only as the issue scopes it.
6. **Compaction/branching behavior** of `before_agent_start`-injected custom messages carrying large skill bodies (context growth, `/tree`, resume) needs a verification test.
7. **Upstream seam request** (Option D): decide whether to file it now (public autocomplete open/refresh or opt-in `/` trigger) so a later release can drop any workaround.

## Addendum: Kimi Code CLI (2026-08-27) — the only production inline-skill implementation on a pi-tui base

[Kimi Code CLI](https://github.com/MoonshotAI/kimi-code) (Moonshot AI, MIT) vendors a **fork of pi-tui** (`packages/pi-tui`) and ships exactly the feature issue #14 wants. It is the strongest existence proof for the design, but its mechanism is the one path Pi UI rules out: editing the editor inside a fork.

### Mechanism

1. **Forked editor, opt-in trigger flag.** `packages/pi-tui/src/components/editor.ts` adds an `inlineSlashTrigger?: boolean` editor option; their `apps/kimi-code/src/tui/components/editor/custom-editor.ts` sets `inlineSlashTrigger: true`. Two helpers:
   - `isAtInlineSlashTrigger()` — the just-typed `/` follows a space/tab mid-line, or opens a later line (`cursorLine > 0`, line is exactly `/`). Then `tryTriggerAutocomplete()` fires on the `/` keystroke.
   - `isInInlineSlashContext()` — regex `[ \t]\/[a-zA-Z0-9.:\-_]*$` (mid-line) or `^\/[a-zA-Z0-9.:\-_]*$` on later lines; keeps the popup alive while the query is typed. Leading line-0 slash stays owned by the native `isInSlashCommandContext` path.
2. **One combined provider.** `apps/kimi-code/src/tui/components/editor/file-mention-provider.ts` handles `@` mentions, line-0 slash commands (fuzzy `scoreTokens` over name + aliases), command arguments, and inline skills in precedence order. Inline-skill branch: token-boundary `/query` mid-input or `/` on later lines, prompt mode only (bash mode treats `/` as a path), items filtered to the skill-only command subset, each item tagged `data: { inlineSkill: true }`. No registered skills → suppress entirely (never fall back to root-directory path completion).
3. **Token-preserving applyCompletion.** For `inlineSkill` items with a `/` prefix, replaces exactly the `/query` span, keeps the leading `/`, appends one trailing space, places the caret after it (`hello /rev` → `hello /skill:review `). Comment notes pi-tui's default mid-line slash apply drops the `/` as if it were a path.
4. **Enter-fills-not-submit, via item data.** Their editor's confirm path still submits when `prefix.startsWith("/")` — but skips submission when `selected.data?.["inlineSkill"] === true`. This is the same trap as Finding (research main body) item 14, solved inside the fork with an item-data flag.
5. **Shared token scanner.** `apps/kimi-code/src/tui/utils/inline-skill-tokens.ts` is the single definition of an inline skill token for autocomplete, editor highlighting, and dispatch: `/` preceded by whitespace (space/tab/newline), name runs to the next whitespace, no internal `/`, name must resolve in the skill command map (with `skill:` prefix fallback); the leading slash-command region is skipped by default. Unknown tokens, paths, URLs, and fractions never match. They also highlight known skill tokens in the editor buffer (`test/tui/components/editor/slash-highlight.test.ts`).
6. **Dispatch bundles activations.** `commands/dispatch.ts`: on submit, `extractInlineSkillActivations(text, skillCommandMap)` (first-occurrence dedupe); a leading `/skill:a args /skill:b` combo or any inline token in a plain prompt becomes one grouped `sendInlineSkillUserInput(text, activations)` (v2 engine). Core activates the skills; the TUI renders a compact `▶ Activated skill: name` card (`components/messages/skill-activation.ts`) instead of expanding the SKILL.md body into the user bubble — the user message stays as typed.

### What transfers to Pi UI (no fork required)

- The trigger/context regex pair (`isAtInlineSlashTrigger` + `isInInlineSlashContext`) and the shared `findInlineSkillTokens` scanner are ~80 lines of pure logic — directly portable as Pi UI's trigger classifier.
- Provider precedence order (args > inline skills > `@`/paths), the "no skills → suppress, don't offer paths" rule, and `data: { inlineSkill: true }` as the marker that distinguishes skill picks from path/command picks.
- `applyCompletion` token surgery preserving `/` + trailing space.
- The `▶ Activated skill` card as the transparency pattern for what was activated.

### What does NOT transfer

- The `inlineSlashTrigger` editor flag and the Enter-bypass at confirm live inside their pi-tui fork. On stock Pi 0.84.x the equivalent requires Option B (`setEditorComponent` wrapper replicating the trigger check before delegating `handleInput`) — their fork is strong evidence that the needed editor delta is small, and strengthens the case for the upstream seam request (Option D): Moonshot maintains a whole fork for this, datspike's UPSTREAM-SEAMS.md asks for it, and #4703 shows upstream accepts such requests.
